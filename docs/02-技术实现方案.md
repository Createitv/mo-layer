# iOS 私密保险箱 App 技术实现方案

## 技术结论

推荐路线：

```text
SwiftUI
+ PhotosPicker
+ LocalAuthentication
+ CryptoKit AES.GCM
+ Keychain
+ SQLite 或 SwiftData
+ FileManager encrypted blobs
+ StoreKit 2
+ CloudKit private database 默认同步
+ iCloud Keychain / Recovery Key 密钥恢复
```

按“一步到位”的路线，1.0 直接采用 CloudKit private database 做默认同步。核心原则仍然不变：CloudKit 只保存密文文件、密文缩略图和加密元数据；明文不离开设备；开发者不自建服务器，也不持有解密密钥。

这里需要注意一个产品边界：默认同步不等于静默上传明文。首次启动时可以默认打开“iCloud 密文同步”，但必须清楚展示数据说明：内容会同步到用户自己的 Apple iCloud，且同步内容是 App 加密后的密文。如果用户没有登录 iCloud、iCloud Drive/CloudKit 不可用、空间不足或网络不可用，App 要自动降级为本地加密保险箱，并持续显示同步状态。

## 架构分层

### UI 层

- SwiftUI 原生实现。
- 解锁页、保险箱首页、导入页、查看器、安全中心、设置页、订阅页。

### 认证层

- 使用 `LocalAuthentication`。
- 支持 Face ID / Touch ID。
- App 启动、后台恢复、导出、删除、关闭同步等敏感操作时触发验证。
- App 内 PIN 作为 fallback。

### 加密层

- 使用 `CryptoKit`。
- 推荐 `AES.GCM`。
- 原始媒体、缩略图、元数据分别加密。
- 明文只短暂停留在内存，不写入长期缓存。

### 存储层

- 文件密文：`FileManager` 存在 `Application Support`。
- 索引数据库：SQLite 更可控，SwiftData 开发更快。
- 密钥材料：Keychain。
- 缩略图：加密落盘，解密后进入 `NSCache`。

### 同步层

- 默认开启 CloudKit private database 密文同步。
- 首次启动检查 iCloud account status。
- 本地写入先成功，CloudKit 后台异步同步。
- 只同步加密后的记录、密文资源和删除墓碑。
- 如果 iCloud 不可用，自动进入本地模式，并提示“待同步”。
- 不使用 iCloud Drive 作为主方案，避免文件冲突和状态不可控。

### 商业化层

- 使用 StoreKit 2。
- 当前权益以 `Transaction.currentEntitlements` 为准。
- 提供恢复购买入口。

## 本地目录结构

```text
Application Support/
  Vault/
    vault.db
    objects/
      item-id.enc
    thumbs/
      item-id.thumb.enc
    temp/
    trash/
```

文件名不使用原始文件名，统一使用 UUID。原始文件名、拍摄时间、标签、相册名都放入加密元数据。

## 密钥方案

推荐分层密钥：

```text
User Authentication
  -> Keychain Master Key
  -> Vault Root Key
  -> Per-File Key
  -> Encrypted Media File
```

### Master Key

- 首次启动生成 256-bit 随机密钥。
- 存入 Keychain。
- 因为默认支持多设备同步，不能只使用 `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`。
- 推荐同时生成本机 Master Key 和可迁移的 Vault Recovery Package。
- 本机快速解锁仍由 Keychain + Face ID 保护。

### Vault Root Key

- 用于包装每个文件的 per-file key。
- 可由 Master Key 解包。
- 可配合恢复密钥或 iCloud Keychain 做迁移。

### 默认同步下的密钥恢复

CloudKit 同步成败取决于新设备是否能解开 Vault Root Key。推荐组合方案：

1. iCloud Keychain 同步一个被用户认证保护的 wrapped root key，用于同 Apple ID 新设备恢复。
2. 首次创建保险箱时生成 Recovery Key，让用户保存。
3. CloudKit 中只保存加密后的 root key package，不能保存明文 root key。
4. 新设备恢复流程为：登录同一 Apple ID -> 拉取 CloudKit 密文索引 -> 通过 iCloud Keychain 或 Recovery Key 解开 Vault Root Key -> 解密每个文件的 per-file key -> 查看内容。

如果用户关闭 iCloud Keychain 且丢失 Recovery Key，新设备即使同步到密文，也无法解密。这个限制要在产品里明确说明。

### Per-File Key

- 每个文件一个随机 AES-GCM key。
- 文件内容用 per-file key 加密。
- per-file key 再用 Vault Root Key 加密保存。

## 导入流程

```text
PhotosPicker 选择资源
  -> 读取 Data 或 File URL
  -> 生成缩略图
  -> 生成 per-file key
  -> AES-GCM 加密原文件
  -> AES-GCM 加密缩略图
  -> 写入 Application Support
  -> 保存加密元数据
  -> 提示是否删除系统相册原件
```

iOS 上不能承诺静默删除系统相册原图。即便通过 Photos 框架删除，也要用户授权和系统确认。产品文案应写成“导入后可选择从系统相册删除，删除由 iOS 授权执行”。

## 查看与缓存

- 图片解密后只在内存展示。
- 视频如果必须生成临时明文文件，使用随机路径，播放后立即删除。
- App 进入后台时清理临时文件和内存缓存。
- 缩略图解密后只放内存缓存。

## 后台遮挡与截图限制

- `scenePhase == .inactive` 时显示隐私遮挡页。
- `scenePhase == .background` 时锁定、清理明文、清理临时文件。
- 监听截屏通知和 `UIScreen.main.isCaptured`。
- iOS 普通 App 不能彻底禁止截图或录屏，只能检测、提醒、遮挡或记录。

## iCloud 同步方案

### 默认方案：CloudKit Private Database

1.0 直接使用 CloudKit private database。用户数据存在用户自己的 iCloud 私有数据库中，开发者不能通过公共数据库共享这些内容。App 端仍然要在上传前自行加密，不能依赖 CloudKit 本身替代业务加密。

推荐 record types：

```text
VaultManifest
- vaultId
- schemaVersion
- encryptedVaultName
- encryptedRootKeyPackage
- updatedAt

VaultItem
- itemId
- type
- encryptedMetadata
- encryptedFileKey
- fileAsset
- thumbAsset
- folderId
- favorite
- updatedAt
- deletedAt

VaultFolder
- folderId
- encryptedName
- sortOrder
- updatedAt
- deletedAt

SecurityEvent
- eventId
- encryptedPayload
- encryptedSnapshotAsset
- createdAt
```

同步内容：

- 加密 manifest。
- 加密媒体文件。
- 加密缩略图。
- 加密文件密钥包。
- 加密文件夹名称和标签。
- 删除墓碑。

### 默认同步写入流程

```text
导入资源
  -> 本地生成 itemId 和 per-file key
  -> 本地 AES-GCM 加密原文件、缩略图、元数据
  -> 写入本地数据库和密文文件
  -> 标记 syncStatus = pending
  -> 后台上传 CloudKit VaultItem + CKAsset
  -> 成功后 syncStatus = synced
```

本地写入必须优先于 CloudKit 上传。这样网络失败、iCloud 不可用或空间不足时，用户导入不会失败，只是显示“待同步”。

### 冲突策略

- 每条记录有 `updatedAt` 和本地 revision。
- 普通元数据使用 last-write-wins，但危险操作要保留墓碑。
- 删除使用 tombstone，不立即物理删除 CloudKit asset。
- 同一个文件在两台设备同时编辑标签/文件夹时，以最近修改为准，并保留安全日志。
- 真实媒体文件不可原地覆盖，编辑后生成新版本。

### 默认开启同步的启动流程

```text
首次启动
  -> 检查 CKContainer.accountStatus
  -> 创建本地保险箱
  -> 生成 Vault Root Key
  -> 生成 Recovery Key
  -> 创建 CloudKit private database schema
  -> 写入 VaultManifest 密文记录
  -> 显示“iCloud 密文同步已开启”
```

如果 iCloud 不可用：

- 继续创建本地保险箱。
- 顶部状态显示“本地保护，等待 iCloud 可用后同步”。
- 设置页提供“重新检查 iCloud”。
- 不阻止用户使用 App。

## 风险点

- 系统相册删除不能静默承诺。
- 视频临时明文文件容易泄漏。
- 默认同步下不能只依赖 Keychain `ThisDeviceOnly`，否则新设备无法恢复。
- `.biometryCurrentSet` 在用户重录 Face ID 后可能导致无法访问。
- CloudKit 同步的核心是密钥恢复，不只是文件同步。
- 默认开启同步必须有清晰状态：已同步、待同步、iCloud 不可用、空间不足、冲突。
- 用户可能误解“不上传服务器”。准确说法是“不上传开发者服务器；开启同步后，密文会同步到用户自己的 iCloud”。
- 入侵拍照涉及摄像头权限和审核敏感点。
- 大视频加解密需要流式处理，避免一次性读入内存。

## 开发里程碑

1. MVP 1：本地加密核心 + CloudKit 默认同步骨架。包括 Vault Root Key、per-file key、AES-GCM、CloudKit private database、VaultManifest、同步状态。
2. MVP 2：图片导入、缩略图加密、Face ID、后台遮挡、本地优先写入、CloudKit 后台上传。
3. MVP 3：视频/文件导入、CKAsset 大文件同步、文件夹、导出、回收站、删除墓碑。
4. MVP 4：新设备恢复。包括 iCloud Keychain wrapped root key、Recovery Key、同步拉取、冲突处理。
5. MVP 5：安全增强。包括 PIN、入侵记录、截屏/录屏检测、伪装入口、同步异常提醒。
6. MVP 6：StoreKit 2、Paywall、免费额度、恢复购买、Pro 同步高级能力。
